Stripe ELEMENTS, not Checkout (client, 10 Oct 2026, the very next thing asked for: "when I press subscribe, let me see some kind of loader ... a nice animation that says the card has declined ... if it's gone through, a nice successful message"). The embedded-Checkout version of this page (9 Oct) drew its OWN button and handled every outcome inside its own iframe, with no event the parent page could see — there was no hook to put GoodTip's own animations on. A Stripe Payment Element, confirmed with ``stripe.confirmSetup()``, hands the result back as a promise instead, so static/js/gt-pay.js owns the whole sequence: a busy overlay while Stripe is asked, a decline overlay with a ten-second countdown back to the card form, a success overlay that counts down to the billing page. What this does and does not change about where the card goes: * The organisation stays on goodtip.com.au the whole way through. * The card fields are still Stripe's own, drawn inside their iframe by the Payment Element. A card number never reaches this server and never appears in a request we handle — which is what keeps GoodTip out of a PCI audit it does not need to be in. * The card is only SAVED here (a SetupIntent). The actual Stripe Subscription — same billing_cycle_anchor, same proration rules — is created server-side once the save succeeds (billing.views.pay_confirm_view). Stripe.js is loaded from js.stripe.com by requirement — it has to be fetched live so Stripe can patch it, and self-hosting it voids the PCI exemption above.
